# Live probe — the MSC4133 write-ACL backport actually protects the DID field

**Date:** 2026-09-10. **Image:** `localhost/siwx-synapse:1.159-msc4133acl`, built from
`siwx-oidc-matrix-server/dockerfiles/Dockerfile` with
`patches/synapse/msc4133-profile-field-write-policy.patch` applied (a backport of
element-hq/synapse#19980 head `d4758f2d2` onto `matrixdotorg/synapse:v1.159.0`).

Run standalone against the **stock** Synapse entrypoint (`/start.py`), SQLite, no MAS
and no siwx-oidc, so that nothing but the patch and its config is under test. Users
created via `registration_shared_secret`; `@adminuser` is a Synapse server admin,
`@alice` is not.

This is an **A/B on one image**: the only thing that changes between the two columns
is whether `experimental_features.msc4133_key_denylist: ["io.inblock.did"]` is present
in `homeserver.yaml`.

## Result

| # | Leg | denylist **CONFIGURED** | denylist **UNSET** |
|---|---|---|---|
| 1 | `ADMIN  PUT    /profile/@alice/io.inblock.did` | **200** | — |
| 2 | `USER   PUT    /profile/@alice/io.inblock.did` | **403** `M_FORBIDDEN` — *"Changing this profile field is disabled on this server"* | **200**, value replaced with the user's own string |
| 3 | `USER   DELETE /profile/@alice/io.inblock.did` | **403** `M_FORBIDDEN` — *"Deleting this profile field is disabled on this server"* | **200**, field removed (subsequent GET → 404) |
| 4 | `USER   PUT    /profile/@alice/io.inblock.nickname` (control) | **200** | — |
| 5 | `USER   PUT    /profile/@alice/displayname` (alias tier) | **200** | — |

Profile state after the protected run, read **unauthenticated**:

```json
{
    "displayname": "Alice Alias",
    "io.inblock.did": {
        "did": "did:key:zDnaeADMINWRITE",
        "proof": "eyJ0ZXN0Ijoi"
    },
    "io.inblock.nickname": "alice"
}
```

## What each leg establishes

- **Legs 2 and 3 vs. the unset column: the vulnerability is real and this closes it.**
  On stock behaviour a plain user overwrote the provider's value with a string of
  their own choosing, and then deleted the field outright. Both were `200`. With the
  denylist configured, both are `403`. Nothing else differs between the columns, so
  the config — and therefore the patch — is the cause.
- **Leg 1: the admin exemption survives the backport.** This is the leg that would
  have failed had we taken an earlier revision of the upstream branch, before
  `f043c26fb` added the `not by_admin and` prefix. siwx-oidc writes this field with a
  minted admin-scoped token, so a guard without that exemption would have locked out
  the provider itself.
- **Leg 4: the denylist is scoped, not a blanket ban.** Other custom profile fields
  stay user-writable. This is why we use `msc4133_key_denylist` and never
  `msc4133_key_allowlist` — the allowlist would have turned this leg into a 403 too,
  forbidding every custom field our users might ever set.
- **Leg 5: the alias tier is intact.** `displayname` remains user-settable, because
  it routes through `set_field` → `set_displayname` and never reaches the guarded
  `set_profile_field`. The three-tier model (user-owned alias / derived MXID /
  provider-owned DID) is enforced **structurally** by where the guard sits, not by
  convention.
- **The final read confirms the object value round-trips** through Synapse's real
  storage path (`encode_canonical_json` into JSONB), and that it is **world-readable
  with no Authorization header** — `require_auth_for_profile_requests` defaults to
  `False`. Nothing private may ever go in this field.
- **The unset column also confirms the registry's "strict no-op" claim**: with
  neither config key present, `_is_profile_field_disallowed` returns `False` and the
  patched server behaves exactly like stock.

## Build-time contract, also verified

The Dockerfile applies the patch with `patch -p1 --forward --batch --fuzz=0` and then
imports both modules. To confirm the failure mode is loud rather than silent, one
context line in the patch was deliberately corrupted and the image rebuilt:

```
Hunk #2 FAILED at 723.
1 out of 3 hunks FAILED -- saving rejects to file synapse/handlers/profile.py.rej
Error: building at STEP "RUN SYNAPSE_PKG=..." : while running runtime: exit status 1
```

A patch that stops applying fails the build. It cannot silently ship an unpatched
Synapse. The patch file was restored and re-verified byte-identical to the upstream
hunks afterwards.

## Caveat carried forward

Enforcement is **prospective**. The guard blocks new writes; it does not validate or
migrate a value written before the config was applied (upstream has the same gap —
Barry3D, `r3783167037`). siwx-oidc closes this from the other side by re-asserting
the field on **every** sign-in, so a pre-existing user-written value self-heals at the
user's next login.
